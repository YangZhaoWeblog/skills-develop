# 架构文档生成指导

> 生成或更新 **.harness/docs/architecture.md** 时读取。唯一骨架为 **[architecture.md](../assets/project/docs/architecture.md)**，修改边界按 **[upgrade-project.md](upgrade-project.md)**。

## 1. 采集证据

用 **rg --files** 定位实际语言的入口、依赖、模块、协议、构建及运行配置，再读取关键代码。不要限定 Go 目录，也不能从文件数量或框架名称直接判断架构模式。

选取实际核心场景，从输入追踪到输出或副作用。调用方向、同步或异步、消息确认及数据归属均需依据实现；不存在的服务、数据库和部署环境不补造。

代码支持某种部署不代表已经上线。必要材料读取失败时报告缺口，不把未知当作不存在；无部署需求时注明不适用，有需求但状态不明时标待核实。

## 2. 按模板说明现状

- **定位与总体视图**：说明项目职责和系统边界，不复制 README 全文；图中可出现必要外部系统，详细上下游清单与契约引用 dependencies.md。
- **模块与关键流程**：记录代码位置、职责、依赖方向、数据所有权和异常边界；技术细节引用实际实现或契约，不复制字段定义。
- **并发与资源生命周期**：说明任务的启动、协作、取消、退出及资源释放责任，不填写另一份容量参数表。
- **决策与约束**：已有理由引用证据；未知历史不得从当前依赖倒推。技术债须有具体代码或记录依据，演进方向只链接已确认计划。
- **部署与公共机制**：按项目实际发布方式及日志、鉴权、配置等机制填写；具体规则和操作引用对应专题，不重复维护。

不要求每个项目都具备服务、容器、数据库或多环境，也不为填满模板添加这些能力。

## 3. 图与文档边界

使用 **Mermaid** 表达真实关系；项目已有且明确偏好其他形式时沿用。总体关系用流程图，时序交互用时序图；图中节点对应真实模块或组件，边说明调用、数据或依赖关系，跨进程通信标明实际协议。

Architecture 维护系统总体视图、内部模块和核心流程；Dependencies 维护外部集成明细及其失败影响。同一流程只维护一份完整说明，另一处保留摘要与链接。

核对图与代码、文内链接及章节引用；不以图数量、决策数量、行数或占位符比例代替内容质量判断。

## 4. 写入与报告

新文件按模板生成。已有文件按 **upgrade-project.md** 融合：保留项目事实和人工内容，在批准范围内更新；存在冲突时说明差异并等待决定。

只给实际核验内容填写 **Source / Last-verified**。报告已说明的范围及具体缺口：必要事实与检查齐备才记完成；材料不足记部分完成，写入或关键读取失败如实报告。
