# 升级与内容保留

> 初始化或更新已有项目时读取。目标是可用的项目规则；文件复制、目录改名和链接创建只是准备动作。

## 1. 确认目标与范围

明确本次项目目录，读取现有入口、配置和未完成任务。多项目仓库的共享入口只管共识与导航，各项目维护自身规则；Git Hook 位于仓库级，命令必须指定正确工作目录。

仅执行本次已授权的操作。文档适配、最小工程和工具接入按 **[SKILL.md](../SKILL.md)** 的边界推进；不修改安装目录，不顺带提交或发布。

## 2. 按内容归属更新

| 对象 | 默认处理 |
|---|---|
| 缺失的长期资料 | 复制对应骨架，再填已核实事实 |
| 已有项目资料、规则与配置 | 保留并比较，按授权融合独有内容 |
| 本 Skill 的标准 Workflow 及工作流模板 | 更新标准章与当前模板；先保留章内项目独有规则，项目新增模板保留 |
| 已建立的产品或开发任务 | 保留原目录、阶段和历史，不套新编号重写 |
| 模型、Hook、工具专属配置 | 保留实际入口，按批准范围修改，验证是否生效 |

模板中的 **PROJECT-CONTENT** 标记以下为项目内容。旧文件无标记，或在标记上方含实际项目内容时，同样保留；不能根据位置判定可覆盖。不要给整个旧文件做一次性替换。

项目规则与新默认规则不一致时，说明差异及影响；已能依用户决定解决的直接处理，尚无依据的交用户选择。不要为统一外观删除有效约束。

## 3. 迁移到当前目录

当前布局为 **.harness/docs/**（长期资料）、**.harness/plans/**（本轮工作）、**.harness/templates/**（可复制表单）。已有其他布局时，先列出旧位置、目标位置、独有内容和受影响引用，再在批准范围内迁移。

构建脚本检测到旧布局或旧专题目录时，只提示合并。**--accept-migrations** 允许准备新布局，不证明旧内容已经迁移；脚本保留旧文件，避免空模板遮蔽已有事实。

产品现状、运行说明、测试规范、数据库说明按职责融合；字段定义继续引用契约或 Schema 源。架构现状按代码核对，保留已确认但尚未落地的选型决策及标记。完成链接修复后，才按授权删除冗余旧入口。

旧任务恢复仍按其自身总览和阶段文件执行。新任务使用当前 **templates/product/** 或 **templates/development/**；不要移动已结束任务来追求目录一致。

旧角色专题 **.harness/agents.md** 按上述迁移边界融合到 **.harness/agent-roles.md**；保留项目职责、权限约束和有效接入摘要，更新入口、阶段模板、任务链接及原生角色配置中的引用。历史执行事实不改写。脚本只提示迁移并保留旧文件；融合完成、引用核对且删除获准后，才移除旧入口。

## 4. 入口与平台配置

**AGENTS.md** 维护项目规则和导航。已有 **CLAUDE.md** 或其他工具入口先读内容；相同规则只保留一份，平台特有部分留在其配置入口。适合使用软链时再创建，已有真实文件或软链不得直接替换。

目录与索引以实际内容为准。标题清楚、规则短而可定位；篇幅较长时下沉专题内容，保留必要的授权边界与项目约束。根入口的内容职责按 **[入口生成指令](init-agent-entry.md#2-按证据填充)** 核对。

升级已有 Index 时，按入口职责区分长期导航与具体任务链接；链接可达不代表应保留。按入口生成指令移除具体任务索引行，保留任务目录、日期、阶段记录及 Workflow 的恢复规则；不能以“保留历史”为由保留错放的导航。

原生 Agent 配置按 **[agent-setup.md](agent-setup.md)** 接入。已有模型选择、权限及工具限制保留；不擅自放宽已有平台限制。

Hook 脚本含 **HARNESS_PROJECT_CHECKS_PENDING** 时只准备不启用。按 **[populate-project.md](populate-project.md#接入检查命令)** 连接项目命令，验证正常与失败路径后再启用。旧脚本中的有效检查和准备步骤须保留。

## 5. 独立交付审阅

接入及调用核验后，派一名**未参与本轮生成的 Reviewer**，用独立上下文审阅最终 Harness。可复用已核验的 Reviewer 角色，无需另建常驻角色。

主 Agent 提供**源 Skill、原项目规则、用户已确认的差异、最终产物及验证记录**。Reviewer 直接读取文件与实际差异，不只接受生成者的完成摘要；只读审阅，缺证据时要求补验，不默认重跑全部检查。

- **入口**：核对 Index 的“何时读取、主题、文件”三列及实际路径；对照 **assets/agents.md**，核对最终 AGENTS 的完整 Workflow 章；阶段表、创建命令、恢复入口与用户批准条件齐全。项目差异须有批准依据，不能用摘要替代原流程。
- **反馈闭环**：核对主 Agent 身份与 **AGENTS.md §2.3** 的判断、派发和返工入口；用不同阶段发现问题的场景核对返回位置、角色权限、受影响验证及独立复审，不能只检查 06 或标题存在。
- **导航职责**：Index 只含跨任务入口，没有具体产品、开发或历史任务链接，也没有新增当前任务登记入口；项目专属长期规则仍可定位。核对原任务文件未因清理索引被改写或删除，并用当前分支与 Overview Meta 验证 §2.5 仍能定位任务；存在歧义时应报告歧义，不能选最新日期代替匹配。
- **任务与 Plan**：核对主 Agent 在隔离目录创建任务的产物与证据，检查 **00–07** 文件及 Plan **§1–10** 是否齐全；缺证据由主 Agent 补验。直接阅读 Plan 模板与副本，重点检查 **§6.1–6.4**、**§9 计划确认**、**§10 完成检查**及跨文件引用；已填写的当前 Plan 同样核对，不能只看文件存在。
- **职责与配置**：AGENTS、角色专题、原生配置及有效权限一致；角色专题保留职责、派发规则、配置入口及简短接入摘要，不堆积执行流水。核对摘要的适用范围，未复验的项不被刷新为通过；根入口不复制接入状态。冲突有用户决定，不能擅自缩减职责后报告完成。
- **事实与证据**：项目内容和历史保留；命令、Hook 和角色的接入结论有实际证据。未知、失败和未执行均如实记录。
- **可读性执行链**：Implement 在 Green 后做必要的最小重构并复测；Verify 核对执行证据，Review 按 code-review.md §1 独立理解、有疑点才比较。不得将明确规则降为可选，或把工具通过当作语义审阅通过。

**记录归属**：对照各原模板核对已填写内容；新增章节或职责变化须有用户确认。检查是否混入无关执行过程或重复记录，不能只检查标题齐全。

**核心流程或必需 Plan 章节缺失，判为不通过。** 返回**通过／不通过、问题位置与依据、缺口及影响**。主 Agent 在授权范围内批量修正或补验，再交 Reviewer 复核；需用户决定的冲突先报告。缺少独立审阅或仍有关键阻塞时，按 **[完成与反馈](../SKILL.md#完成与反馈)** 报告未完成。
