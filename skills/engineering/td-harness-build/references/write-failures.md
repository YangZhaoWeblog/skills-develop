# 失败记录生成指导

> 维护 **.harness/docs/failures.md** 时读取。记录范围、复盘方法和验证要求统一见 **[failures.md](../assets/project/docs/failures.md)**。

## 1. 定位相关证据

优先读取本次消息、当前任务记录、执行输出及项目已有失败记录。需要补查历史时，遵守 **AGENTS.md** 的任务读取边界；只查与问题相关、已获准读取的项目资料，不默认扫描所有分支或全部 Memory。

初始化时可从已授权的项目历史中定位候选问题。修复类提交、revert、重复修改和记忆条目只是线索；核对具体变化与原始记录后，才能描述失败事实。没有实际验证，不把记忆中的“已解决”直接写为完成。

## 2. 核实并写入

按模板记录期望、实际、原因、处置、复验及改进建议。事实与推断分开；有证据的失败但原因不明时写“待核实”，仅有提交标题不能编成事故。

重要记录写入项目自定义区，按时间倒序；已有记录和归档历史保留，避免为同一事件新增同义条目。没有符合条件的失败时不凑内容、不编造示例事故。

复盘提出的建议不等于实施授权。规则修改沿用已批准范围，越界按项目确认规则处理；独立审阅或工具试跑不能称作 AI A/B 实验。

## 3. 报告缺口

区分**没有资料、读取失败、未核实、已验证**。资料不存在可以说明后继续；权限、命令或读取错误须报告缺口，不能静默当成没有失败记录。

未知字段保留待核实状态，不强填根因或修复结论。只记录实际执行的验证方法与结果；新增规则是否有效，按模板要求检验，不以写入成功代替效果证据。
