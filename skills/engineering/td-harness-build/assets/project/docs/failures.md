# 失败记录与复盘

> 发现重要失败时在当前阶段记事实，06 Review 修正复验后收口。分析原因，提出改进；不要求每条失败都变成规则。

## 1. 记录范围

保留重要遗漏、重复犯错、费时排查、隐蔽兼容问题及 AI/流程失误。正常 TDD 跑红或立即修正的偶发小错，不机械归档。没有重要失败时，不新增记录。

## 2. 复盘方法

先读本次消息、相关阶段记录和执行输出，核对期望与实际。检查已有规则是否被读到、工具是否接通、失败是否被正确报告；原因不明就写“待核实”。

| 原因 | 改进方向 |
|---|---|
| 代码或测试错误 | 修代码、补测试，不默认改 Harness |
| 已有规则或工具未起作用 | 修入口、澄清旧规则或修检查工具，不重复加规则 |
| 未覆盖的重要问题，且可能再次出现 | 补最小规则、正反例或确定性检查；严重问题不必等第二次 |
| 收益尚不明确 | 保留证据和待核实项，不把猜测写成硬约束 |

能自动判定的优先用现有工具；需要判断的用规则和正反例。无效或重复规则可建议删除。改进建议不自动授予修改 Harness 的权限；沿用已批准范围，越界按 AGENTS 处理。

## 3. 改进后的验证

**验证修复**：用新版重做失败案例，再检查正常案例。只测新版（B）能说明这些案例的结果，不能证明新版优于旧版。

**比较收益**：需要判断新增规则的价值时，让旧版 A、新版 B 完成同一任务，比较遗漏、误改及额外操作成本。两边均通过，不足以证明新增规则有收益；不要求每次文档修改都做 A/B。

**隔离上下文**：测试 AI 行为时，每次使用不继承讨论或答案的独立 Agent／会话和独立初始副本。不提示漏项、不读取另一组输出；A/B 保持模型、工具、任务和起始文件等条件相同，只改变待评估规则。

**记录结果与限制**：一次成功只是初步证据，不稳定时复验。方法、实际结果和限制写入 §4 的“本次处置与复验”；未执行不能写有效，不额外要求报告文档。

## 4. 记录模板

每条独立成节，按时间倒序。只留必要原文或链接，敏感信息脱敏。

```markdown
### YYYY-MM-DD：一句话现象

- 事实与证据：期望、实际及原始记录入口。
- 原因：已核实的原因；不明写“待核实”。
- 本次处置与复验：做了什么，实际结果是什么。
- 改进建议：仅记录 / 修旧规则 / 补规则或正反例 / 加检查 / 删无效规则。
- 处理状态：待核实 / 待处理 / 已完成；完成时注明实际改动位置和验证依据。
```

提出建议不能写“已完成”；原有记录和归档历史保留。
