# 验证规则

> **用途**：**Plan** 选择检查，**Implement** 获取早期反馈，**Verify** 记录证据，**Review** 独立验收时读取。
>
> **命令来源**：实际工具版本、固定命令和项目门槛分别维护在测试、编码和环境规范中；沿用项目入口，不让 **Agent** 每次重新找工具或拼命令。

**Verify 执行核验**：优先用确定性工具，结合必要的实际操作，核实行为、指标和执行证据。**Review 独立语义审阅**：判断设计、职责与阅读负担是否合理，方法见 **[code-review.md §1](code-review.md#1-审阅准备)**。工具通过不等于设计合理或代码好读，审阅意见也不能替代执行证据。

## 1. 检查选择

按本次改动及风险选择检查，并在 **02-plan.md §6.4「本次检查清单」** 写明范围、执行入口、通过条件和选择依据。

| 检查 | 适用范围 |
|---|---|
| **基础检查** | 每个任务执行适用的低成本检查：代码的格式、编译/类型、静态检查；文档的链接和结构 |
| **单元测试（Unit Test，UT）、覆盖率与函数质量** | 代码改动的相关行为与回归；非行为改动不制造无意义的新测试。函数门槛见 **§2「通过标准」** |
| **集成测试（Integration Test，IT）** | 改动影响真实 **DB**、上下游或组件协作时，执行相关真实依赖检查；**SQL** 查询语义变化须有有效真实 **DB** 证据 |
| **变异测试（Mutation Testing）** | 按业务行为风险和测试有效性需要选择；纯拼写/注释不机械执行 |
| **用户流程验证** | 影响界面和操作路径时执行实际交互，**API** 结果不代替界面验证 |
| **验收测试（Acceptance Test，AT）** | 本次 **验收条件（Acceptance Criteria，AC）** 必须验证；能证明 **AC** 的 **UT／IT** 可复用，不重复维护同义用例 |

**项目强制门禁仍须执行**，包括安全检查、**持续集成（CI）** 和 **Git Hooks**。凭证、外部输入、权限及依赖漏洞按项目基线检查；不因改动行数少而豁免，也不要求每个任务执行全部检查。

确实不涉及的检查说明原因。**工具缺失、环境不可用或未执行，不等于“不涉及”**。范围或风险变化时更新 **Plan**；超出批准范围先确认。

### 1.1 测试复用

已有 **UT／IT** 能证明某条 **AC**，且结果适用于 **当前版本、环境和范围** 时，**AT** 引用对应测试和结果。结果不再适用时重跑，仍缺少证据的 **AC** 另行验证。

### 1.2 环境准备

需要部署测试版本时，优先使用项目 **CI/CD** 或已有部署入口。**发布本身属于本次目标时**，**Plan** 须写明授权、回退方式和发布后检查。

### 1.3 验证手法选择

下表按要回答的问题列出手法。本次用哪些由 **02-plan.md §6.4** 决定，并写明通过条件；没有列入手法的问题，直接按原检查结论处理。

| 要回答的问题 | 手法 | 用在哪一步 | 要点 |
|---|---|---|---|
| 声称行为不变，是否真没变 | **差分对比** | Verify | 输入取现有测试、边界值，必要时加真实样本；预期差异先写入 Plan；只出现预期差异才算等价。对象身份与时序按契约需要比较 |
| 两版写法哪个更好 | **A/B 盲测** | Review | 维度先写明；隐藏来源并对调顺序；评判者用独立上下文；按理由归纳，分歧交用户。方法见 **code-review.md §1** |
| 测试是否真能发现问题 | **变异测试** | Verify | 由工具逐项改动实现；存活项按等价变异或覆盖缺口处置，等价项须独立核验，详见 §2 与 **04-verify.md §6** |
| 自建测量或工具是否可信 | **独立复算** | Verify | 用另一套方法重算同一指标（另一工具或人工抽样）；全部一致，或每处差异都解释到原因，才算通过 |
| 只改注释或格式，逻辑是否未动 | **AST 等价对比** | Verify | 仅改注释：去注释后逐字节比；改格式：按语法树逐节点比，忽略位置 |
| 规则或工具声称能防某问题 | **对抗用例** | Verify 构造执行／Review 判定 | 主动构造绕过写法（等价改写、移入回调、间接调用）；未被暴露的绕过记为工具缺口，写入规则说明，撤回对应的覆盖声明 |

“行为一致”与“哪个更好”是两类问题，不能互相替代；自评不算盲测。

## 2. 通过标准

下表是新项目默认值。已有项目的明确门槛继续保留，冲突先确认，**不得检查失败后自行降低门槛**。列出标准不代表工具已经接入。

| 检查项 | 默认通过条件 | 范围/说明 |
|---|---|---|
| **圈复杂度（Cyclomatic Complexity）** | ≤10 | 新增／修改函数；确认工具按“超过 10”判失败，而不是“达到 10”判失败 |
| **认知复杂度（Cognitive Complexity）** | ≤15 | 新增/修改函数 |
| **CRAP** | ≤10 | 使用同版本有效 **UT** 覆盖数据；100% 覆盖时 **CRAP** 仍等于圈复杂度 |
| **嵌套深度（Nesting Depth）** | ≤4 层 | 新增控制结构；不因历史已有超标而扩大清理 |
| **UT 覆盖率（Code Coverage）** | ≥80%，关键行为测试有效 | 本次改动范围；不能用全仓平均掩盖当前缺口 |
| **变异测试（Mutation Testing）** | 选定范围内有效变异被测试发现，无未处置的未覆盖或存活项 | 等价变异可凭证据经独立核验排除；执行错误不算检测成功 |
| **重复代码（Code Duplication）** | 工具标出的重复片段已处理，或有经独立核验的保留理由 | 结构相似不等于业务规则相同，不设零重复率或按次数强制抽象 |
| **架构依赖（Architectural Dependencies）** | 无禁止依赖方向或循环 | 依赖数量仅作观察，语义分层仍由独立审查核对 |

### 2.1 超标处理

新增代码按门槛修正；历史问题记录基线，**本次引入或加重的问题须处理**，不扩大为无关重构。

先核对测试、输入数据和实际代码结构，再决定改法。**不为降分机械拆函数、制造抽象或弱化断言**；例外按授权规则确认，不以反复申请例外代替修正。

### 2.2 旧代码重构

**重构旧代码前须取得用户同意**；同一方案已有明确批准时，不重复询问。申请时说明具体问题、改法、影响范围，以及如何验证行为不变（可用 §1.3 差分对比）。

默认用短文字和必要代码示例说明；结构难以表达时再加图，不强制图片、**HTML** 或额外文档。完成后，将实际变化与验证结果写入当前阶段记录并汇报。

## 3. 执行与复验

### 3.1 执行顺序

**Implement** 按 **测试驱动开发（Test-Driven Development，TDD）** 逐行为推进：**跑红 → 最小实现转绿 → 必要时最小重构并复测 → 下一个行为**。重构保持行为不变并遵守授权，具体边界见 **[TDD 规范](testing/tdd.md#循环规则)**。**Plan** 先列用例，不等于先写完全部测试。

**Verify** 先做基础与复杂度检查，**UT 成功并生成同版本有效覆盖数据后，再计算 CRAP**。**IT、AT、变异测试及 §1.3 选用的手法（A/B 盲测归 Review）** 按 **Plan** 执行；高风险技术或环境先探测，不机械按耗时排序。

### 3.2 证据记录

**04-verify.md** 记录版本、实际命令、必要数值和关键原文；输出留在终端，**不要求另建报告**。覆盖率文件及工具临时产物按需使用。

**IT** 留关键日志和适用的 **reqid／trace**；**UI** 留实际操作与结果。不贴无关全量日志，不只写链接或“符合预期”。**变异测试须逐项核对**，不能只看退出码或总百分比。

函数质量检查优先使用可靠的增量筛选；不支持时，在相关模块全量计算，对照 **git diff** 确定新增／修改函数，并独立核验。

### 3.3 检查无法完成

**检查失败须返回失败状态**，不能被后续 **echo、SKIP** 或成功命令覆盖。区分 **通过、失败、未执行、不涉及**；缺工具或环境时，报告缺口、准备方法和重跑命令。

**必要检查未完成则停止**；用户明确同意跳过后，在 **04-verify.md** 记录未验证项、原因与剩余风险，不能标为通过。

### 3.4 修正与复验

一轮检查后，汇总问题、核对证据及授权，**批量修正并独立复验受影响项**。批准范围内不逐次询问；**需用户决定的阻塞立即报告**，不等整轮结束。

**04-verify.md §7「失败处理与复验」** 保留首次失败、原因、修正及复验结果。未受影响的证据按 **§1.1「测试复用」** 引用。

## 4. 独立验收与授权

### 4.1 Review 核对内容

按 **.harness/docs/code-review.md** 独立核对需求、规则、设计与交付证据，**不默认重跑全部检查，不另设数值门槛**。

语义问题须给出位置、规则和理由，不凭“太长”或“感觉不好”阻断。测试核对独立预期、有效断言及 **AC** 覆盖，不能只看覆盖率。

> eg:（示例）可复用的无状态业务转换函数放在 **RPC Logic**，违反项目的 **helper** 分层约定；即使测试通过，仍须纠正。

架构工具能准确检查的项纳入固定入口，不重复手抄指标。

### 4.2 用户确认

独立验收、修正复验及 **Docs** 完成后，**人工审查最终版本**，结论写入 **06-review.md §6「最终结论与人工确认」**。个人项目按“谁会发现、多久发现、损失多大”选择重点；团队强制人工审查不能省略。

人工发现问题后，**修正 → 复验 → 再审**；旧批准不适用于修改后尚未审阅的版本。

确认条件统一见 **AGENTS.md §2.6「用户确认」**。需求或 **AC** 有问题时停止，提供依据与产品原文入口，更新并重新核验后继续；不能悄改 **AC** 或掩盖前置遗漏。
