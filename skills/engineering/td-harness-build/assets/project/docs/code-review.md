# 代码审阅（Code Review）规范

> **用途**：独立核对实际改动、需求与验证证据，判断能否交付。**作者自检不能替代独立 Review**，也不默认重跑 **Verify** 的全部检查。
>
> **记录位置**：本任务的发现、处置与确认写入 **06-review.md**；数值门槛见 [验证规则](verification.md)，工具命令沿用项目规范。

## 1. 审阅准备

审阅当前 **diff** 及必要上下文，记录实际看过的版本与范围，不假称逐行检查全部代码。按“谁会发现问题、多久发现、损失多大”确定重点。

交接材料从当前任务读取：

- **需求与范围**：由 **00-overview.md §3** 定位产品需求与 **验收条件（Acceptance Criteria，AC）**，核对已批准的 **02-plan.md**。
- **验证与文档**：读取 **04-verify.md** 的当前版本结果和 **05-docs.md** 的增量；区分通过、失败、未验证和不涉及，无文档变化时说明原因。
- **记录归属**：对照原模板核对各任务文件的章节与内容职责，检查是否混入其他阶段的执行过程或重复记录；不能只检查标题齐全。
- **关键决定与风险**：在 **06-review.md §2「作者交接」** 摘要，详细内容引用原记录。

提交不得夹带无关改动、敏感文件或误提交的生成产物；禁止提交 **.env、*.key、*.pem、credentials.json** 及编译产物。禁止直推保护分支，按项目特性分支与 **PR／MR** 规则提交。

**PR** 说明背景、改动、影响、验证和回滚方式，按需关联 **Issue**。删除已有测试须说明理由；引入新依赖须在 **Commit Message** 说明理由。

## 2. 审阅清单

逐项核对本次适用内容。**明确规则和项目强制约束必须满足，工具通过或严重度较低不能豁免。** 启发式提示与设计建议须说明具体位置、问题依据及影响，不凭个人偏好阻断。

### 2.1 业务与安全

- [ ] 符合需求与 **AC**，无范围蔓延；检查空值、长度、并发、重试和幂等等相关边界。
- [ ] 错误处理完整，不静默吞错；忽略错误（如 `_ = err`）有明确理由。
- [ ] **SQL** 参数化；命令调用采用结构化 **API**；路径访问检查穿越风险（如 `..`）。
- [ ] 不硬编码密钥、**AK／SK**、密码及内部 **IP**；日志不泄露身份证、手机号、**Token** 或密码。
- [ ] 鉴权、操作权限与数据权限完整；外部输入按白名单及校验规则处理。
- [ ] 加密遵守项目规范，不使用 **MD5／SHA1／DES／RC4**。

### 2.2 资源与测试

- [ ] 资源申请与释放配对，无线程、**goroutine、Promise** 或订阅、监听、缓存泄漏；**Context** 正确传递并响应取消。
- [ ] 行为改动覆盖适用的正常、边界与异常场景，保留逐行为红绿证据；非行为改动有适用检查。
- [ ] 测试断言使用独立预期，能发现真实行为错误；契约明确规定的消息可作断言。
- [ ] 集成测试使用真实 **DB**，不以 **Mock DB** 替代。
- [ ] 本次适用质量门禁通过，或例外已明确获准；不按行数或个人折行偏好阻断。

### 2.3 编码与设计

- [ ] 新增／修改的手写函数符合 [中文步骤分块规范](coding-style.md#中文步骤分块强制)：注释准确、简短；编号与实际处理阶段对应，阶段内不同处理组有空行分隔，不只检查编号或空行是否存在；不合格须修正。
- [ ] 已按 [可读性与接口设计](coding-style.md#23-可读性与接口设计) 核对接口负担、表达与结构；读取实际实现及必要调用位置，不仅接受作者自检结论。
- [ ] 命名一致，必要取舍有说明；职责、分层和依赖合理，不为不存在的需求增加抽象或配置。
- [ ] 重复代码候选已核对是否属于同一业务规则，不按重复次数强制抽象。
- [ ] 错误路径、日志、链路标识和必要指标能支持排查。
- [ ] 核对 **N+1**、不必要的全表扫描及内存浪费；遵守项目框架约定，如 **go-zero** 的依赖注入与 **Context** 透传。

### 2.4 AI 生成内容核验

- [ ] 方法、字段、包、导入及错误码常量**真实存在**。
- [ ] 第三方库版本与用法符合 **go.mod、package.json、requirements.txt** 等实际依赖文件。
- [ ] 业务逻辑符合真实数据流；超时、阈值、限流等数值有依据，不凭空编造。

按场景检查国际化文案、**API** 与数据库迁移兼容性，以及 **README、ARCHITECTURE、OpenAPI** 等文档是否同步。

## 3. 审阅意见与处理

每项写清**文件位置、问题、依据、影响和修改建议**，记录在 **06-review.md §3「Review Findings（审阅发现）」**。不凭“太长”“更优雅”要求重构。

| 严重度 | 判断依据 | 处理要求 |
|---|---|---|
| 🔴 **高** | 安全、数据或关键业务行为受到实质影响 | 作为阻塞问题处理，不带未解决问题合入 |
| 🟠 **中** | 局部行为、可靠性或维护性存在明确风险 | 修正或说明处理决定；违反强制规则时仍阻断 |
| 🟡 **低** | 不影响正确性及强制规则的局部改进 | 可选改进；不采纳时说明理由 |

**严重度描述影响，处理状态记录结果**；澄清问题单独记录，不作为严重度。

每条意见须回应：采纳、不采纳，或暂缓并关联跟进事项。有分歧、不采纳或申请例外时，在 **06-review.md §4「讨论与决议」** 记录依据和决定。未回应的意见或未解答的澄清问题不能直接关闭。

## 4. 独立验收与合入

先处理独立 **Review** 的发现，修正后独立复验；再由人工确认最终版本。**修改前的批准不能用于修改后尚未审阅的版本**。

- **个人项目**：独立 AI 验收后，由用户确认最终版本与 **Submit** 授权。
- **团队项目**：另须满足项目的人工 **Reviewer** 和合入规则，不能由 AI 替代。

合入前须确认：**阻塞问题已解决、意见已回应、无未解答的澄清问题、无 Security Critical 告警**，项目要求的 **CI** 门禁通过。不存在或不适用的检查不能记为已执行。

批准范围内的修正按 [验证规则](verification.md) 执行；越界、需求或 **AC** 变化、未授权副作用及必要验证缺口，按 **AGENTS.md §2.6「用户确认」** 处理。

## 5. 紧急修复（Hotfix）

仅适用于生产事故、安全漏洞或强制下线。**紧急情况不自动豁免审阅与授权**；按项目明确的紧急流程执行，没有专门约定时沿用正常门槛。

例外须说明风险、待补验证及跟进安排，经用户或项目规定的授权人确认。复盘记录在 [failures.md](failures.md)。
