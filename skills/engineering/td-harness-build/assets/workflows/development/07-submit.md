# 07. Submit

> **执行角色**：Executor；派发与权限见 **.harness/agents.md**。
> **用途**：按用户授权提交代码、推送远端或创建 PR。
>
> **前置条件**：Verify 已完成必要检查，Docs 已按需更新，Review 已确认最终版本与 Submit 授权范围。
>
> **提交策略**：默认一个 PR 对应一个 commit（one-PR-one-commit）；后续修正按 §4 amend 流程处理。项目另有明确约定时，按项目规则执行。
>
> **授权边界**：只执行获准操作；合并、发布另行授权。禁止直推保护分支，禁止裸 `--force`。

## 1. 前置检查

| 项 | 结果 |
|----|------|
| 当前分支 |  |
| 目标分支 |  |
| Review 结论与批准版本 |  |

验证后代码有变化时，补做受影响的验证并更新 **04-verify.md**，不得沿用失效结果。

## 2. 执行顺序

| # | 动作 | 执行要求 |
|---|------|----------|
| 1 | 编写 commit message | 填入 **§3「Commit Message（提交说明）」** |
| 2 | 预登记任务完成 | 更新 **00-overview.md** 的时间记录 07 行结束时间与耗时、Meta 状态、关键决策；开发进度的 07. Submit 标为已完成（预登记） |
| 3 | 暂存本次改动 | 使用明确文件路径执行 `git add`，包含本次代码、任务记录和相关文档 |
| 4 | 创建 commit | 首次提交一个 commit |
| 5 | 推送／创建 PR | 仅执行获准操作，向用户报告实际结果 |
| 6 | 处理后续修正（发生时） | 按 **§4 amend 流程**处理，仅改批准范围的代码与测试，并完成受影响验证与复审 |

**预登记不代表提交成功**：push、PR 合入和上线结果以实际 Git／平台状态为准，另向用户报告；操作失败不能报完成。

**边界点 A**：完成步骤 1、2 后，**00-overview.md** 和本文件冻结。

**边界点 B**：PR 合入后，任务冻结。

---

## 3. Commit Message（提交说明）

```text
<type>(<scope>): <subject>

<body>
```

按项目提交规范填写；需要关联事项时，在末尾添加 `Closes #123` 或 `Refs #123`，不要将占位内容和填写提示写入实际提交。

允许类型：

`feat|fix|docs|style|refactor|perf|test|build|ci|chore|revert|other`

---

## 4. amend 流程

已有本任务 commit、PR 尚未合入，且修正完成验证与复审后，按以下命令更新原提交；命令保留原 commit message，需要调整说明时去掉 `--no-edit`。

```bash
git add -- <本次批准的文件>
git commit --amend --no-edit
# 仅已推送且 push 授权仍有效时：
git push --force-with-lease
```

> 修正仅限批准范围的代码和测试；不得夹入无关改动。冻结后的任务记录不回写；需要改变需求或 **02-plan.md** 时先停止处理，不借 amend 扩大范围。

---

## 5. 完成检查

- [ ] Commit Message 与本次实际改动一致。
- [ ] **00-overview.md** 已按 §2 完成预登记。
- [ ] 实际 commit 已核对，仅包含本次批准的文件与改动。
- [ ] 获准的 push／PR 操作已成功；未获准项明确未执行。

冻结后按本清单核对实际结果并向用户报告，不回写冻结文件；预登记不能作为操作成功的证据。
