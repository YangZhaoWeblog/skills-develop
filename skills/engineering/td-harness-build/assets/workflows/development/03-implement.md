### 3.1 红绿证据

**行为改动**：按 Plan 的单元测试（Unit Test，UT）用例，先运行测试并确认目标行为失败（Red），再以最小实现使其通过（Green）；逐行为推进，已有测试保持通过。

仅在本次改动出现明显代码坏味道或规范违规时，按授权范围做最小重构（Refactor）；无具体问题则记录“无需重构”。**非行为改动**写“不涉及 TDD”，按 Plan 的验证命令执行并在 §3.3 记录结果。

**禁止为通过测试而弱化断言或修改业务契约。** 测试失败时，先核对需求、验收条件（Acceptance Criteria，AC）与独立预期；批准范围内的问题修正后复验，越界或需求 / AC 有问题时停止并确认。

**通用**

- [ ] 无硬编码凭证 / Token / 密码
- [ ] SQL 全部参数化，无字符串拼接
- [ ] 外部输入均有校验
- [ ] 错误路径有日志，包含上下文
- [ ] 关键路径有指标 / trace 埋点
- [ ] 无死循环 / 无边界递归

**并发 / 性能**

- [ ] 共享状态有锁或无状态化
- [ ] 长循环是否让出调度（协程项目必查）
- [ ] 不在请求处理中做 O(n²) 以上的计算
- [ ] 外部调用有超时设置

**错误处理**：日志应说明失败操作及必要上下文，避免只有“error”；异常应向上传递或明确恢复，不静默吞掉。
